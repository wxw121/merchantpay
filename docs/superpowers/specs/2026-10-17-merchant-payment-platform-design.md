## 1. 建设目标与成功标准

建设一个面向多商户的支付与对账平台，提供支付受理、渠道交互、部分退款、账务记录、渠道对账、差错处理、结算单和运营控制台。项目同时作为高级 Java 工程实践载体，要求在重复、并发、乱序、超时、进程中断及大数据量下保持明确的业务结果。

用户已确定支付方向，并具有交易、账户或金融系统相关经验。以下默认假设用作本次需求基线：人民币单币种、单地域部署起步、独立渠道模拟器、面向学习与可复现的工程验证。未知的个人硬件配置不影响需求编写；性能验证另外使用固定参考环境。

| 目标编号 | 成功标准 |
| --- | --- |
| OBJ-01 | 商户能走通收款、查询、部分退款、账单查看及结果通知闭环 |
| OBJ-02 | 一笔有效业务事件最多产生一次有效记账；每组分录按币种借贷平衡 |
| OBJ-03 | 并发退款满足额度约束；超时和结果未知不会被当作失败而重复扣款或释放额度 |
| OBJ-04 | 账单差异可识别、可追溯、可审核处理；原始账务记录保留 |
| OBJ-05 | V3 在指定参考环境完成 5,000 支付 TPS、独立 20,000 查询 QPS、亿级历史数据验收；分别及混合压测 |
| OBJ-06 | V3 完成发布回退、备份恢复、单节点故障、数据重放和路由迁移演练 |
| OBJ-07 | 三版内交付前后端、部署说明、契约、测试、数据生成器、压测与演练报告；没有留给 V4 的必需能力 |

“成熟”表示这些范围和验收条件全部满足，不表示已获得真实资金运营资格或已经证明任意硬件上的性能。

## 2. 业务边界与术语

### 2.1 三版内范围

- 人民币 CNY；多商户隔离；API 凭证与管理端账号。
- 支付受理、渠道请求、结果查询、异步通知、关闭与迟到结果处理。
- 全额和多次部分退款；退款查询、退款额度预占与释放。
- 平台视角的渠道应收、商户应付及手续费账务；商户端展示其应收金额。
- 渠道交易账单与退款账单导入、匹配、差异处理、重跑及审核。
- 商户结算单的计算、审核、明细分配和模拟核销；已结算后的退款调整。
- 交易追踪、任务进度、数据统计、权限审计、故障演练与性能验证。
- 两个模拟支付渠道贯穿三版；V2 完成支付宝开放平台官方沙箱适配器。

### 2.2 范围之外

真实银行清算和出款、真实商户进件及身份核验、银行卡信息采集、用户充值钱包、信用授信、多币种兑换、跨境税务及争议拒付。它们有独立的资金和业务模型，不能通过多加几个页面纳入当前版本。

官方沙箱默认选支付宝开放平台，以其当前支持产品和官方接口为准。账号与应用凭证需要用户自行提供；凭证缺失时适配器与契约测试可以完成，但报告必须标记官方联调未验证，不能据此宣称外部接入验收通过。核心负载和故障验收使用可控模拟器。

### 2.3 统一术语

| 术语 | 定义 |
| --- | --- |
| 支付单 | 平台受理的一次商户收款意图，具有稳定的商户业务号与平台支付号 |
| 渠道尝试 | 针对某支付单向特定渠道发起的请求，保留请求键、参数摘要及结果证据 |
| 结果未知 | 尚无权威证据判断成功或失败，继续查证；不等同于失败 |
| 业务事件 | 有唯一业务标识和版本的已提交事实，例如支付成功、退款成功 |
| 记账凭证／分录 | 一次记账的业务来源与借贷明细；通过追加调整纠错 |
| 对账批次 | 针对渠道、业务日、账单类型和账单版本的一次核对任务 |
| 差错单 | 对账或运行期间发现的不一致及其证据、处理状态和审核轨迹 |
| 结算单 | 某商户在明确截止水位内的可结算金额及组成明细，不等于银行已到账 |
| 模拟核销 | 在演练中确认一张结算单已模拟支付；所有相关界面和记录显示模拟标记 |
| 业务日 | 账单指定时区中的自然日；本项目固定 Asia/Shanghai |
| 完整性水位 | 已确定处理完成的分片事件位置和账单版本集合；不是单纯的本机时间 |

## 3. 角色与权限

| 角色 | 可以执行 | 限制 |
| --- | --- | --- |
| 商户研发 | 管理本商户 API 凭证、查看集成日志和通知、调试沙箱 | 不得访问其他商户数据或平台密钥 |
| 商户运营 | 查看本商户交易，提交授权范围内的退款申请 | 不可直接修改账务或批准自己的高风险操作 |
| 商户财务 | 查看账单、结算单、退款与手续费，申请导出 | 仅本商户；导出受审计及有效期控制 |
| 平台运营 | 查看交易链路、查单、重发通知、发起差错处理 | 不可强行把未知支付改成成功，不可直接改账 |
| 平台财务制单人 | 差错处理提案、账务调整申请、结算单试算 | 不可审核本人申请 |
| 平台财务复核人 | 审核或驳回差错调整、结算单、模拟核销 | 身份独立；审批对象版本变化后原审批失效 |
| 运维 | 管理任务、查看指标、执行授权演练和发布 | 不因运维角色自动取得账务调整权限 |
| 审计员 | 只读查看操作轨迹、账务凭证及审批证据 | 不可发起资金类变更 |

V1 实现租户隔离、基本角色和审计；V2 完成制单／复核分离。所有授权以服务端为准，前端隐藏按钮只用于交互提示。

## 5. 关键业务规则

### 5.1 金额与手续费

1. CNY 最小单位为分；接口金额使用十进制整数字符串。支付金额范围为 1 至 1,000,000,000 分，退款金额大于零且受原支付额度限制。
2. 业务运算使用整数或带明确精度和舍入方式的十进制数；禁止 `float`／`double` 参与资金运算。汇总采用足够精度并检查溢出。
3. 默认演示费率为 0.6%，四舍五入到分；手续费不得超过支付金额。费率在支付受理时留存版本快照，后续改费率不改旧交易。
4. 累计应退手续费 = 原手续费 × 累计成功退款金额 ÷ 原支付金额，四舍五入到分；本次应退手续费为累计值与此前已退值的差。
5. 多笔退款可并发处理，成功记账时在原支付单锁内按本次成功后的累计金额计算手续费差额。渠道响应顺序变化不影响最终累计金额。
6. 业务发生时间、平台处理时间、渠道完成时间、账单业务日分别存储。时间戳以 UTC 存储，业务日按 Asia/Shanghai 计算。

### 5.2 幂等与身份

- 支付业务唯一键为商户 ID 与商户支付业务号；退款唯一键为商户 ID、原支付号与商户退款业务号。
- 相同业务键、相同有效参数重试返回同一对象及其当前状态；有效参数不同返回 `IDEMPOTENCY_CONFLICT`。
- 临时请求去重缓存不是业务幂等的唯一依据。数据库唯一约束、状态版本和业务事件唯一键共同保证正确性。
- 三版演示数据保留窗口为 365 天；期间保留业务幂等记录或归档后的去重索引。Redis 过期和热表归档均不允许业务号重新收费。
- 归档完整业务明细时，在线保留支付控制记录，包括原实付、累计退款、有效预占、费率快照、账务来源与路由。历史退款仍以该控制记录为原子额度边界，不依靠分析库推算额度。
- 一个渠道尝试结果未知时，保持原渠道和原请求键查证；不得另起一个新尝试绕过未知状态。
- 渠道标识、商户标识、金额、币种和业务关联必须共同校验。回调验签通过不意味着可以跳过业务匹配。

### 5.3 支付状态

| 状态 | 含义 | 允许的后续处理 |
| --- | --- | --- |
| PROCESSING | 已持久化受理，正在发起或等待渠道结果 | 成功、明确失败、结果未知或关闭流程 |
| UNKNOWN | 存在已发出的渠道尝试，但缺少权威最终结果 | 查单、回调查证、产生差错；不能凭次数耗尽改为失败 |
| CLOSE_PENDING | 已请求关闭，渠道尚未确认关闭且未证实成功 | 等待确认或成功结果；保留追踪 |
| SUCCEEDED | 已验证渠道成功且支付与账务事务提交 | 查询、退款；不回退为失败 |
| FAILED | 渠道明确失败且确认没有成功扣款 | 查询，按规则可创建新的商户业务单 |
| CLOSED | 渠道已明确关闭且确认没有成功扣款 | 只读；矛盾成功证据进入差错流程 |

并发状态转换采用数据库条件更新或行锁。正常成功证据与关闭竞争时，以权威渠道结果查证；若真正终态发生矛盾，不静默覆盖终态，应记录异常并通过差错及调整流程处理。

### 5.4 退款状态与额度

退款状态包含 `PROCESSING`、`UNKNOWN`、`SUCCEEDED`、`FAILED`。在同一原支付的本地事务中执行：

`累计成功退款金额 + 有效预占退款金额 <= 原支付实付金额`

退款请求受理时预占额度；成功时从预占转为成功金额并记账；明确失败才释放。结果未知保持预占并进入查证队列。重复回调和查单不能重复结转或重复释放。

### 5.5 记账模型

账簿采用平台视角的借贷记账。第一版即使用凭证与分录模型，而不是上线后替换金额模型。

演示：支付 100.00 元，手续费 0.60 元：

| 方向 | 科目 | 金额 |
| --- | --- | --- |
| 借 | 渠道应收 | 100.00 |
| 贷 | 商户应付 | 99.40 |
| 贷 | 手续费收入 | 0.60 |

随后退款 30.00 元，按规则退还手续费 0.18 元：

| 方向 | 科目 | 金额 |
| --- | --- | --- |
| 借 | 商户应付 | 29.82 |
| 借 | 手续费收入 | 0.18 |
| 贷 | 渠道应收 | 30.00 |

要求：

- 一组记账凭证必须同币种借贷平衡，且业务事件唯一。校验、写入凭证与分录、推进业务状态、写入 Outbox 在同一分片本地事务内提交。
- 支付与退款都跟随原支付分片，账务保持共置。V3 分片不得破坏这一原子边界。
- 每笔交易写追加分录，不在每次交易上锁住商户级单一累计余额行。商户汇总余额属于可重建投影，并带有处理水位。
- 已过账分录禁止直接编辑、删除。差错调整通过有来源、有审批、有唯一执行键的新凭证处理。
- 结算截止时从权威分录核对可分配金额；不得直接用实时分析图表中的汇总金额生成结算指令。
- 模拟渠道收款核销及模拟商户核销使用独立演示科目，并明确标注模拟；它们不能被展示为真实银行资产。

### 5.6 对账与结算

- 每个账单对象保留原文件、摘要、渠道、业务日、生成时间、版本、币种、笔数与金额合计；解析失败保留错误行但不发布半份有效结果。
- 对账分为准备、解析、匹配、差异发布、复核及封版；每阶段可续跑，结果版本不可混用。
- 流式预对账用于尽早发现异常；最终对账必须等待完整渠道账单及相关账务水位，不以窗口超时证明资金事实。
- 差错单状态为 `OPEN → INVESTIGATING → PROPOSED → APPROVED/REJECTED → EXECUTING → RESOLVED`；执行失败可重试。无须调整的差异需记录说明及证据后关闭。
- 本地未知、渠道成功且证据核实一致的支付，可以按既有成功处理规则补单；金额冲突及人工账务调整必须独立复核。
- 结算以明确水位的分录和差错冻结金额为依据；跨分片先形成可恢复的分配记录，再生成最终结算单。
- 每个来源可结算金额只允许有效分配一次。过期预占须依据结算任务状态恢复或释放，不能只靠锁超时。
- 已模拟结算后的退款生成负向调整，抵扣下期金额；净额为负时结转，不生成负数出款单，不修改原结算单。

### 5.7 默认运行阈值

- 商户 API 请求签名时间窗口为 300 秒，参数摘要绑定请求体；业务重试可使用新请求时间和原业务号。渠道通知遵循各自官方签名规则，不能套用商户 API 的通用窗口拒绝合法迟到通知。
- 渠道连接超时默认 500ms，单次调用总超时 2s；超时只影响调用结果，不判定资金失败。
- 未知结果在 2 分钟内优先查证，超过 2 分钟告警，超过 30 分钟进入人工关注队列；24 小时后转长期查证任务。任何阶段都不因时长到期自动释放未知退款额度。
- 自动查单使用有上限的指数退避和抖动，间隔从 1 秒增长到最多 5 分钟，且遵守渠道配额；任务总量与最老任务年龄受监控。
- 商户结果通知最多自动重试 24 小时，之后隔离并允许授权重发；通知失败不回滚已成功支付。
- 单分片待发布事件达到 100 万条、估算占用 1 GiB 或磁盘剩余不足 30% 时，任一条件触发新业务限流；恢复到事件／占用阈值 50% 以下且磁盘空间恢复后再解除。已受理业务与回调恢复使用预留资源。

这些默认值可在测试报告记录后调整，但不得改变未知状态、有效入账与额度约束的语义，也不得隐去调整对性能和恢复目标的影响。

## 6. API、事件与数据契约

### 6.1 API 范围

提供版本化 `/api/v1` 接口，至少包含支付提交／查询／关闭、退款提交／查询、账务查询、对账批次与差错、结算单与审批、异步导出与任务、商户与凭证管理。V1、V2、V3 是产品版本，不意味着每版都破坏 API 路径。

约束：

- 服务端生成请求与 trace 标识；业务幂等键和关联号在响应中返回。
- 响应明确区分接口受理、业务状态、渠道状态和通知投递状态。
- 标准错误至少包括未授权、签名无效、幂等冲突、参数不合法、额度不足、状态冲突、限流、依赖不可用、结果未知。
- `GET` 及分页游标绑定当前权限与查询条件；单页最多 100 条。查询精确 ID 不依赖遍历全部分片。
- 管理端采用 OIDC 会话；商户服务间 API 使用独立凭证与 HMAC-SHA256 请求签名。具体渠道适配遵循该渠道官方签名协议。
- 管理端会话使用 Secure、HttpOnly、适当 SameSite 的 Cookie，并对变更请求实施 CSRF 防护；不在浏览器持久化长期服务端凭证。导出通过鉴权下载入口访问，下载时重新验证用户、商户、任务归属和有效期；转交链接不授予其他用户访问权。
- 通知地址与文件下载受 SSRF 防护、域名与 IP 校验、超时和大小限制。上传文件及浏览器输入均视为不可信数据。

### 6.2 事件范围

事件信封包含 `event_id`、`event_type`、`schema_version`、`merchant_id`、`aggregate_id`、`aggregate_version`、`occurred_at`、`trace_id`、`logical_shard`。金额字段以字符串编码。

- 同一业务事实在发布、重试与重放时保持同一 `event_id`；变更后的新事实产生新版本。
- 消费侧按业务标识与版本幂等；不能只依赖 Kafka offset 或一个短期 Redis key。
- 事件按支付根聚合键分区；跨聚合不要求全局顺序。商户汇总采用可交换聚合与完整性校验。
- 只承诺可验证范围内的至少一次传递加业务幂等；Kafka 事务不被当作 MySQL、ClickHouse、外部支付调用的全局事务。

### 6.3 数据实体

核心实体包括商户、账号与角色、API 凭证、支付单、渠道尝试、退款单、退款预占、原始通知、业务事件、记账凭证、账务分录、Outbox、消费幂等记录、对账批次、账单文件与明细、差错单、审批单、结算单与来源分配、导出任务及审计记录。

具体物理表、索引及接口字段属于后续详细设计；本说明书已经约束其业务唯一性、关联关系、金额含义、权限和原子边界。

## 9. 成熟交付门槛

V3 交付必须同时满足：

1. 本说明书全部 FR、NFR、CH 要求有实现或验证证据；范围外事项没有被误报为已实现。
2. 正常流程、边界、并发、重复、乱序、故障、补数、重放和迁移用例全部通过；无未解决的资金正确性与高危权限缺陷。
3. V3 参考环境完成指定吞吐与大数据验收，并提交原始结果、配置、数据清单及账务核对报告。
4. 前端能实际完成商户收款查看、退款、差错处理、审批、结算单、导出与审计流程；没有以固定假数据代替的核心页面。
5. 官方沙箱联调状态独立披露；模拟演练与真实外部验证明确区分。
6. 新环境按照部署文档可以启动；备份可恢复；旧数据可迁移；旧事件可重放；发布失败有回退路径。
7. 所有必须能力在 V1、V2、V3 中闭合。后续小版本只用于修复和兼容维护，不能承接三版中未完成的核心要求。

## 10. 需求变更规则

新增需求必须说明替代或压缩哪一项原范围，以及对吞吐、数据、正确性和版本门槛的影响。性能数字调整必须附相同口径下的测量证据；不能以“下一版优化”绕过当前大版本验收。
