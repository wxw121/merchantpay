# 三个大版本规划

日期：2026-10-17。依据：[需求说明书](../superpowers/specs/2026-10-17-merchant-payment-platform-design.md)。

## 1. 规划原则

项目只设 V1、V2、V3 三个大版本。每版都形成能部署、能演示、能测试的完整增量。支付与账务正确性从 V1 就成立；V2 强化并发和故障恢复；V3 完成规定规模、数据治理和运维交付。不能先交付会重复扣款、超额退款或记错账的版本，再把修正写成后续优化。

下文的性能、容量与时效均为验收目标，执行环境与口径统一见[验收文档](../quality/performance-and-resilience.md)。小版本只是对应大版本内的里程碑，不增加第四个大版本。

## 2. 总览

| 维度 | V1：业务与正确性闭环 | V2：并发、可靠性与财务流程 | V3：规模化与成熟交付 |
| --- | --- | --- | --- |
| 产品结果 | 可收款、退款、查账、识别差异 | 可处理差错、审核调整、生成并模拟核销结算单 | 可运行亿级历史数据、实时分析、扩容迁移与恢复 |
| 部署形态 | 模块化业务应用 + 独立模拟器 | 多业务实例 + 独立工作进程，事务核心仍共置 | 交易核心分片；独立数据处理与分析服务 |
| 数据链路 | MySQL Outbox 轮询与可重试任务 | CDC Outbox → Kafka，消费者幂等；ClickHouse 查询投影 | Flink 流批处理、历史归档与大规模查询 |
| 支付完成 TPS | 300，持续 15 分钟 | 2,000，持续 30 分钟 | 5,000，持续 60 分钟 |
| 独立精确查询 QPS | 2,000 | 8,000 | 20,000 |
| 支付单 | 100 万 | 1,000 万 | 1 亿 |
| 账务分录 | 500 万 | 5,000 万 | 5 亿 |
| 业务事件明细 | 1,000 万 | 1 亿 | 10 亿 |
| 账单处理 | 10 万行，10 分钟内 | 100 万行，15 分钟内 | 1,000 万行，30 分钟内 |
| 稳定性运行 | 4 小时 | 12 小时 | 24 小时 |
| 前端交付 | 商户与平台基础工作台 | 完整财务工作台、审批、任务和故障视图 | 数据工作台、历史检索、规模下交互与导出 |
| 必需证据 | 正确性、契约、基础压测 | 并发、故障、财务闭环、链路核对 | 大数据、容量、迁移、灾备、全部需求追踪 |

三个维度分别验收：独立支付峰值、独立查询峰值、混合业务负载。不得把各自峰值相加后当作同一时间已承载的流量。

## 3. V1：建立可信的业务与账务基础

### 3.1 发布后的用户能力

商户可以创建支付，查看处理结果并接收通知，发起全额或部分退款；平台可以查看渠道尝试和账务，导入账单并识别差异。面对重复通知、请求超时和重启，系统保留足够证据并能继续处理。

### 3.2 里程碑

| 里程碑 | 工作内容 | 可验收结果 |
| --- | --- | --- |
| V1.1 接入与最小支付链路 | 前后端基础、账号与租户、商户 API 签名、两个独立模拟渠道、支付提交／查询／回调 | 商户端可完成一笔真实数据库中的模拟收款；验签、越权、幂等冲突测试通过 |
| V1.2 退款与记账 | 支付和退款状态机、额度预占、手续费取整、凭证和分录、Outbox 任务 | 支付成功和入账同事务；并发退款不超额；重启重试不重复入账 |
| V1.3 对账与交付 | 账单导入、逐笔匹配、差错只读及查证、交易时间线、基础监控、自动测试和部署 | 能导入有预置差错的账单并精确识别；压测和 4 小时运行完成 |

### 3.3 必须攻克的技术问题

- CH-01／CH-02／CH-03：支付幂等、未知结果恢复和退款额度约束。
- CH-04 基础：状态、分录与 Outbox 同事务；轮询发布任务具备租约、重试和消费幂等。
- CH-05 基础：重复账单幂等、断点续跑、差错证据与结果版本。
- 数据模型预留稳定业务号、事件版本与逻辑分片键，但第一版不强制部署分布式数据库。

### 3.4 交付清单

1. 后端、前端、独立模拟器及基础设施 Compose 配置。
2. API 契约、商户接入示例、角色权限矩阵、支付／退款状态规则、记账规则及数据迁移脚本。
3. 可复现数据集和负载脚本；至少覆盖支付成功／失败／未知、重复回调、退款并发、乱序和进程中断。
4. 基础账务核对报告、10 万行账单报告、300 TPS 支付完成与 2,000 QPS 独立查询报告。
5. 前端端到端演示：下单 → 成功 → 部分退款 → 查账 → 导入差错账单 → 查看证据。

### 3.5 发布门槛

所有 V1 功能通过；核心不变量零违反；吞吐按 R1 环境达到目标；4 小时稳定性运行通过；重新部署不丢任务，回调持久化后重启能恢复；没有高危越权或签名绕过缺陷。

V1 的差错以识别和查证为主，不开放无复核的手动改账。正式调整与结算流程由 V2 提供。

## 4. V2：并发正确性、可靠交付和财务流程

### 4.1 发布后的用户能力

平台在多实例和依赖故障下维持可恢复的支付处理。财务可以对差错提出处理方案、独立复核、执行调整，并生成带来源明细的结算单和模拟核销。一个官方沙箱适配器完成外部协议契约验证。

### 4.2 里程碑

| 里程碑 | 工作内容 | 可验收结果 |
| --- | --- | --- |
| V2.1 可靠事件链路 | Kafka KRaft、Debezium Outbox、幂等消费、重试与隔离、契约版本、追踪 | 发布器切换不丢事件；重放 3 次账务不增重；故障消息能定位和恢复 |
| V2.2 财务处理闭环 | 差错提案／复核／执行、调整凭证、结算明细分配、模拟核销、负向结转 | 制单复核分离；金额变化使审批失效；同一来源不可重复有效结算 |
| V2.3 并发与高可用 | 多实例、限流与背压、渠道隔离、读模型、数据库单成员切换、官方沙箱适配 | 2,000 TPS 和 1,000 万支付单目标通过；混合负载及故障恢复通过 |

### 4.3 关键工程决策

- 交易状态、退款额度、权威账务和 Outbox 继续共置于一个事务核心，避免为增加服务数量引入资金双写。
- 通知、对账、导出、分析投影使用独立工作进程与资源池，防止长任务耗尽支付连接与 CPU。
- CDC 替换轮询采用有边界的切换：记录 Outbox 高水位，等待旧发布链路排空，启动 CDC，并按稳定事件 ID 去重。禁止无水位地长期开双发布器。
- Redis 用于缓存、配额和短期控制；退款额度、业务幂等和有效记账仍由 MySQL 约束。
- ClickHouse 用于查询与统计投影，其延迟不阻止 OLTP 正确受理。正式对账与结算使用权威流水及已确认水位。
- 官方沙箱采用其签名与回调协议；不把模拟器的统一协议误当成真实渠道协议。

### 4.4 交付清单

1. Kafka／CDC 部署与恢复文档、事件契约与兼容策略、重复／乱序／重放测试。
2. 差错和账务调整审批、结算单与模拟核销的后端和前端完整流程。
3. 未知结果、退款预占、死信重放、通知失败、渠道不可用的任务与告警视图。
4. 并发退款、热点订单、热点商户、数据库成员故障、Kafka／CDC 暂停、Redis 故障的演练报告。
5. 官方沙箱适配器与脱敏联调报告；没有凭证时单列外部联调未验项，不能签署外部接入完成。
6. R2 上 2,000 TPS、8,000 QPS、100 万行账单及 12 小时稳定性报告。

### 4.5 发布门槛

V1 全部回归继续通过；V2 功能与安全门槛通过；MySQL 业务事实、Outbox、Kafka 事件和读模型可以按业务键核对；应用与单个数据库成员故障恢复符合约定；财务审批、模拟核销无绕过路径。

V2 结束时，CH-01 至 CH-05 必须完成并发与故障强化，不能继续作为 V3 的未完成业务功能。V3 可以提升它们的规模上限。

## 5. V3：高并发、大数据与成熟交付

### 5.1 发布后的用户能力

平台支持亿级历史交易及分片部署，提供实时运营分析、可校正的流式预对账、完整日终对账、历史查证和大批量导出；团队能执行版本升级、分片搬迁、数据重放与灾备恢复，并证明正确性没有被扩展破坏。

### 5.2 里程碑

| 里程碑 | 工作内容 | 可验收结果 |
| --- | --- | --- |
| V3.1 交易分片与历史分层 | 16 个逻辑桶映射到 4 个物理分片、交易与账务共置、去重索引、冷热归档、可恢复结算分配 | 同商户流量可跨支付根分布；历史退款正确路由；业务唯一键不因迁移失效 |
| V3.2 流批数据链路 | Flink 指标与预对账、ClickHouse 明细／聚合、对象存储 Parquet、迟到修正、重放与重算 | 10 亿事件装载；重复与迟到不导致最终指标增重；重建后与权威事实核对一致 |
| V3.3 完整规模与运维 | 全规模压测、限额／降级、容量与成本报告、Kubernetes 部署、迁移／灾备、完整端到端回归 | 5,000 TPS、20,000 QPS、1,000 万账单行和 24 小时运行通过，证据包完整 |

### 5.3 必须完成的规模化能力

- CH-06：支付根分片、热点保护、按商户配额、有限重试及依赖背压；不使用单个商户余额行串行化全部支付。
- CH-07：1 亿支付单、5 亿分录、10 亿事件的实际装载与分层，在线精确查询、历史任务、离线核对分别验收。
- CH-08：流式状态、乱序、迟到、重复输入、checkpoint 恢复、全量重放和投影重建；流批结果在封版水位下核对。
- CH-09：事件与 API 兼容、数据库扩展／收缩迁移、滚动发布、备份恢复、路由搬迁及旧请求隔离。
- CH-10：跨分片结算来源预占、失败恢复、负向退款调整和唯一有效核销。

### 5.4 明确的规模边界

1. 峰值 5,000 TPS 是参考环境中唯一成功支付并完成记账的吞吐，不是空接口能力。
2. 20,000 QPS 是独立精确查询场景；支付、退款、列表、分析和导出还须按混合场景验收。
3. 亿级历史数据采用热、温、冷分层。查询最近 30 天与查询一年前归档交易有不同响应目标，界面明确区分。
4. 不承诺持有全部历史事件的 Kafka 长期在线保留；Kafka 是传递及短期恢复通道，长期可重放事实保存在已校验的归档中。
5. 正确性优先于无界吞吐。超额流量可被限流；请求一旦明确受理就必须持久化并继续恢复处理。

### 5.5 交付清单

1. 最终前后端、模拟器、流批任务、部署配置、运行手册与版本兼容清单。
2. 全部需求与测试追踪表；CH-01 至 CH-10 对应到可执行用例与报告。
3. 参考环境账单、CPU／内存／存储／网络配置、软件镜像摘要、数据规模清单、数据生成种子。
4. 规模装载报告、独立与混合压测原始数据、稳定性报告、账务全量／增量校验报告。
5. 节点故障、积压回补、分析重放、历史退款、分片搬迁、发布回退及备份恢复演练报告。
6. 完整演示剧本：支付结果未知 → 查证成功 → 并发退款 → 对账差异 → 审批调整 → 结算单 → 历史查证。

### 5.6 发布门槛

全部需求、性能、数据规模、安全及恢复门槛通过；高优先级缺陷清零；官方联调状态如实披露；新环境重建和恢复步骤可执行；最终账务及差错核对一致。

若资源不足而未执行完整规模测试，版本状态标记为“功能完成，规模验收未完成”，不得宣布 V3 成熟交付，也不能仅凭预测或单机缩比结果豁免。

## 8. 人力、工期与资源安排

默认单人每周投入 15～20 小时，可做如下初始排期：V1 约 6～8 周、V2 约 8～10 周、V3 约 10～14 周；另留约 20% 缓冲，合计约 29～39 周。这是包含前端、数据平台及验证的规划估算，不是工期承诺。

优先按可验收里程碑推进。压缩时间时先收紧界面装饰、非核心报表数量和自动化部署便利功能，不能删减账务正确性、权限隔离、必需规模验收或故障恢复。

个人设备承担日常开发和缩比数据验证；R2／R3 参考环境用于阶段性集群实验。先测算容量和资源费用，再安排测试窗口；本规划不授权自动购买服务器或启用付费云资源。

## 9. 版本完成报告模板

每版报告必须列出：代码版本与镜像摘要、完成的需求编号、环境资源、数据种子及实际规模、测试执行时间、指标原始文件、正确性核对结果、未验项及阻断缺陷、演练恢复结果、已知范围限制。

只有本版门槛全部满足，才能标记“已发布”。三版内没有完成的核心需求必须如实记录为未完成，不得移动到一个未定义的 V4。
