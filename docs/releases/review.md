# V1 独立审查与处理

2026-10-18，一次独立 fresh-context 全量源码审查，reviewer 为 gpt-6-astra。目录没有 Git，审查直接覆盖实际源文件、需求、计划和取舍台账；没有伪造提交范围，也未派生二次审查。审查未确认重复扣款、超额退款、非平衡记账或跨商户读取 Critical；这不是生产安全认证。

## Important 修复范围

| 原问题 | 修复 | 针对性验证 |
| --- | --- | --- |
| 导出缺少用户归属和有效期 | V8 保存 OIDC sub / 24h expires_at；创建、列表、签名游标、下载同时绑定当前用户与商户；过期 410，其他用户 404；无归属旧文件需重新生成 | ExportTest、SecurityIntegrationTest：同商户不同用户、过期、角色撤销 |
| 批任务失租后仍可写状态 / 替换文件 | 每个检查点锁定并验证 outbox lease；V9/V10 聚合 run_token 另防同一批次的独立人工重试；每个执行 token 独立 ZIP，数据库指针仅当前执行可发布 | H2 / MySQL 对账与导出：旧执行暂停 → 同任务重领或新重试任务完成 → 旧执行恢复，不回退状态或替换快照 |
| 平台与渠道业务日来源不同 | 模拟渠道请求传平台持久化 createdAt 为 businessCreatedAt，独立保存渠道处理时间和稳定业务时间；账单按上海业务受理日取数，迟发 / 跨日恢复不挪日 | ChannelStoreTest：支付及退款临近午夜受理、次日发送仍归原业务日 |
| 成功后矛盾失败 / 关闭被忽略 | 不改变资金终态；相反终态报 CHANNEL_EVIDENCE_CONFLICT；统一 ChannelGateway 保留证据，Inbox 标 CONFLICT；相同终态仍幂等 | 金融测试保留成功与额度，ChannelEvidenceTest 验证 Inbox / 同步归一化均留证据 |

最初已观察到新导出归属 / fencing API 缺失的编译失败，以及旧失败证据不抛冲突的两个行为失败；修复后持续回归。所有最终通过数量及日志入口以 [交付记录](v1.0.0.md) 为准。

视觉 QA 另发现退款并发提交时，详情页头与账务分录可能来自两个时刻；已用真实 MySQL 在两次读取间提交退款复现（3 条旧分录预期却返回 6 条），改为只读 REPEATABLE_READ 快照后通过。负载 QA 又补入站并发上限和连接耗尽的可重试响应，验证过载不进入业务逻辑、异常后名额释放；这些是实际 QA 发现后的修复，不冒充独立 reviewer 原始结论。

## 审查保留事项的判定

- R1/D1、300 完成 TPS、四小时长稳仍是阻断正式发布的门槛，功能审查不能豁免；若误判会造成容量承诺失真。
- S3 / OpenAPI 生成客户端 / k6 已在交付差异中声明；当前本地文件、类型契约、Java 负载器满足缩比可复现入口，不等于这些目标已接通；若需跨主机使用须补适配。
- Docker 应用镜像与远程 CI 不能从定义文件推断通过；已记录 DockerHub 网络失败，仍须实际部署验收。
- 本机 HTTP Cookie、模拟 Webhook 接收器仅为固定本地演示；真实部署必须重新验证 TLS、身份与回调；误当生产配置会暴露凭据。
- 至少一次通知允许重复投递，接收侧必须按 eventId 业务去重；错误当成恰好一次会重复执行业务。
- 退款按两端各自确认顺序分摊手续费，累计值仍正确；单笔差异进入对账，当前不要求双方确认顺序相同；误要求会错误回写已确认账务。
- 当前角色模型没有细分商户管理员；以现有角色与服务端商户范围为权限准则，不宣称已覆盖 V2 制单 / 复核或更细角色设计；未来扩角色须重做权限矩阵。
