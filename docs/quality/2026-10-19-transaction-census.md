## 真实统计与口径

| 指标 | 空闲 | 低速 | 并发 |
| --- | ---: | ---: | ---: |
| 计划 / 受理 / 入口503 | 0 / 0 / 0 | 100 / 100 / 0 | 3000 / 2948 / 52 |
| Binlog_cache_use增量 | 0 | 1562 | 36273 |
| 每笔受理对应的窗口缓存使用次数 | — | 15.62 | 12.304 |
| 显式COMMIT摘要次数增量 | 见原始摘要 | 2268 | 21575 |

| READ_WRITE访问模式事务事件 | 1392 | 3574 | 59975 |

`Binlog_cache_use`表示使用过binlog事务缓存的事务数，可能包括回滚；它是服务器全局计数，不能直接等同于已提交支付事务或fsync次数。[官方状态变量定义](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html)规定该口径。表内比值是整个窗口增量除以受理数，包含后台任务与结束核验时间，不能逐笔归因。

事务READ_WRITE按访问模式统计，空事务和仅做查询的普通事务也可能进入该类；不能把59975当成写入提交数。[官方事务汇总说明](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-transaction-summary-tables.html)明确包含空事务及访问模式差异。空闲窗口binlog缓存增量0而redo同步计数增加219，进一步说明fsync不能全部归属支付。

两次端点之间实际约21.28/23.10/77.29秒，包含查询、独立账务观察及排空，不仅是发送窗口；完成TPS仍由原计量V2给出。低速完成区间4.95–5.00/s、完成P99上界496444µs；并发48.883–49.133/s、P99上界889911µs。没有正规600秒预热，不能据此通过稳定基线、300完成TPS或R1。

## 源码中的持久化边界

| 边界 | 已合并内容 / 独立提交原因 |
| --- | --- |
| nonce持久化 | 在配额和业务之前独立提交；后续429、数据库失败或业务回滚不能让已消费nonce重新可用 |
| 配额检查 | 既有10ms目标分组，同key/秒聚合，数据库提交后才逐请求分配额度 |
| 支付受理 | 支付记录、持久化容量、任务和操作审计共用业务事务；Controller与Service的嵌套TransactionTemplate不是两次独立提交 |
| 任务领取 | 同批领取共用事务，租约在调用渠道前落库；空轮询也可能有显式COMMIT |
| 渠道准备与回执 | PREPARED、查询NOT_FOUND、最终回执分别持久化，原始回执必须在业务结果之前保存；网络不进入结果事务 |
| 渠道结果 | 支付终态、释放容量、复式账务、成功任务及attempt最终状态已共用事务 |
| 回调Inbox | 接收原文与处理任务同事务；后续结果应用与Inbox终态同事务，重复结果仍检查幂等 |
| 商户通知 | HTTP前保存SENDING，HTTP后保存投递结果；可靠任务确认仍逐条校验租约并分组提交 |

这些边界不是一张固定的“每支付提交次数”清单：领取/确认/配额会分组，回调与主动结果存在竞态，重试/未知/退款分支也不同。直接删除原始回执保存、把网络包进事务或把所有TransactionTemplate合并，都会改变故障恢复语义。

并发组的表级I/O采样与合法交易增长相符：nonce、支付、凭证各2948次INSERT，渠道attempt2948次INSERT/8844次UPDATE，任务8844次INSERT/17688次UPDATE，通知记录2948次INSERT/2948次UPDATE。它们反映操作量，不能直接换算事务数。

## 工具复核与限制

本次`.work/TransactionCensus.java`为临时只读探针，规范化SQL仅在内存分类，持久化固定类别、计数、instrument名称及配置，不保存SQL、摘要、凭据或业务标识。所有原始端点、98份当时源码/工具及SHA-256已冻结；后续加强探针是不同版本，不改写历史样本。

独立复核发现的精度边界已明确记录：并发nonce摘要COUNT_STAR增量2947，而表级INSERT为2948；凭证摘要2945，表级和资金事实为2948。该差异不作为产品丢账证据，也不猜测统计欠计的具体原因。分析结果分开记录`intervalValid=true`与`exactCommitAttributionVerified=false`、`exactStatementCountsVerified=false`，不能将区间可用解释成精确计数通过。

原探针按`LAST_ERROR = NULL`识别ACK，实际规范化摘要使确认进入`OUTBOX_RENEW_OR_OTHER`，因此该类别保留为合并桶，不能当作续租次数。原快照也未采集digest丢失计数及statement/table instrument状态；全局查询未返回Com_commit/Com_rollback，缺失不补0。后续对照探针另补相关状态和真实归一化ACK识别，不倒填旧证据。
