# V1 并发优化与复测（2026-10-22）

**结论：已确认代码优化有效，V1 完整性能目标仍未达标。** 同资源支付对照由约48 TPS提升到94.5 TPS，但后者仍有52次503，不能作为合格容量。当前零错误测量为支付58.5 TPS、独立退款31.1 TPS、独立查询599.8 QPS；支付和退款的受理尾延迟仍超标。没有发布。

## 保留的修改

- 修复实际`@ImportHttpServices`渠道代理的Apache连接池：每个地址从默认5连接改为可配置64，总连接上限为两倍，连接租借最长等待2秒。原JDK客户端配置只覆盖账单读取器。真实HTTP阻塞测试验证配置12时只允许12路到达，旧实现只能到达5路。
- FAST后台工作并发由固定30改为有界可配置，普通启动仍30，Performance启动采用96，允许范围1..256。单次数据库领取保持最多64，96个名额分64+32领取，归还未领取名额。BULK仍独立限额。
- 导出旧任务覆盖测试改为由样本的持久化时间确定查询区间，消除“刚创建记录恰好等于排他上界”的时序波动；租约和文件内容断言保留。

没有修改资金事务、双1、nonce先持久化、签名配额、回执先于结果事务、幂等与租约fencing。源码仍Java25 / Spring Boot4.1.1，不增加中间件。

## 未采纳的实验

1. 渠道回执提交分组：前一日ABA未稳定优于原版，已恢复原实现。
2. nonce提交分组：300QPS的原版P99为25.42/46.29ms，候选45.88ms，成功QPS均约299.92，无稳定收益，整体撤回。审查发现的候选事务超时分类问题随撤回消除。
3. 增加资源：应用4CPU/2GiB、MySQL8CPU/4GiB/cache2GiB。支付320/秒＋退款32/秒测120秒得到72.48/19.98完成TPS；2050/秒查询测120秒得到1096.70成功QPS，P99 4013.79ms。预热也有容量拒绝，不能作为合格容量，未设为默认配置。
4. MySQL原生组提交：同一高预算下临时设置5000微秒/32事务，保持双1；2050/秒查询120秒候选1245.25QPS，恢复默认后1239.08QPS，均有大量错误，未采纳。参数已恢复0/0，未写入持久配置。该参数可合并binlog同步，也可能增加竞争，参见[MySQL8.4官方说明](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html#sysvar_binlog_group_commit_sync_delay)。

## 瓶颈证据与范围

实际HTTP池5连接与固定30后台名额已经由失败测试证实并修复。原2CPU数据库在测量窗口有触及CPU预算的采样；扩大CPU后仍不达标。高预算诊断区间中COMMIT累计等待1615.6秒、nonce插入累计1208.6秒；redo/binlog单次文件等待最大约704.7/646.0ms。过期nonce清理累计1.605秒、最大494ms，未成为主要累计耗时。

这些累计时间包含并行等待，不能相加当作墙钟。文件等待的最大值也不能单独区分物理磁盘、Docker虚拟磁盘和宿主机调度的占比。当前剩余问题是提交路径的尾部停顿与负载过量时的数据库竞争，扩线程、扩CPU及本次提交分组实验未解决。

全程保留金融历史。查询采用32个真实管理员API创建的隔离测试商户，每个key仍限500/秒；1024笔样本均经支付API生成。查询80%随机＋20%固定热点，范围是这些凭据所属全部在线样本，**不是完整D1历史范围**；全库资金不变量检查仍覆盖原有金融数据。历史多商户分布、正式10分钟预热/15分钟三轮、独立R1环境与D1容量认证均未通过本轮补齐。
