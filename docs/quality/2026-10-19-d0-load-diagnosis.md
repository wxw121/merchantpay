# V1 压测计量修正与 D0 瓶颈诊断

日期：2026-10-19（北京时间）。本轮完成计量工具修正、短时阶梯测量与瓶颈取证；版本仍为 `1.0.0-SNAPSHOT`。**没有通过 R1 的 300 完成 TPS、2000 查询 QPS、D1 或四小时长稳验收。**

结构化结果：[load-measurement-v2.json](../releases/evidence/load-measurement-v2.json)；执行计划：[load-v2-query-plans.json](../releases/evidence/load-v2-query-plans.json)。原始报告、逐请求记录和诊断样本留在 `.work/performance`，摘要保存其来源及 SHA-256，不包含凭据。

## 计量变化

- 每笔计划请求有固定业务号，同时保存计划时间、实际发送时间、HTTP 结束时间和响应结果。503 / 超时后逐业务号查证；它们实际持久化的订单不能抵消另一笔 202 的未完成。
- 独立 READ COMMITTED / autocommit 连接，在一条 SQL 中观察成功状态、支付来源凭证、至少两条且借贷平衡的分录和对应 Outbox；只有已提交事实可见。轮询不使用应用连接池。
- 提交时间只能约束在“上次不可见查询开始—首次可见查询结束”之间，首个样本下界为实际发送时间。全部使用负载机的单调时钟，避免应用 / 数据库时钟偏差；不再按 `ledger_journals.created_at` 归窗。
- 到达窗完成数及成功 P99 都报告上下界。最终延迟从计划发送时刻开始，包含负载机调度、HTTP、异步队列与过账；另列 HTTP / 调度延迟。全体受理请求的 P99 上界考虑未完成样本，无法约束时为 `null`，并报告未完成数和最长等待年龄。
- 终态失败、未完成、未确认 HTTP 但已持久化分别列出；HTTP 传输异常也保留延迟。退款响应与主支付阶段统计分开。纯查询没有做资金校验的字段为 `null`。
- `moneyInvariantsPassed` 与整个负载是否无错误分别报告；503 保留为负载失败。`referenceR1Certified` 始终为 `false`。

独立复核后补齐两处边界：失败采样的等待成本也计入观察开销；资金凭证预期按最终一致快照中的成功支付加成功退款计算，明确失败 / 仍在处理的支付不误报资金不平。`correctnessPassed` 仍是当前默认全成功模拟渠道负载的完整检查，不能代替允许明确业务失败的正式标准负载。另修复小样本退款比例，最终源码30支付+20%退款实测为6退款、36凭证、差额0；此前30笔误选20退款的原始报告保留。修复及验证范围见[独立复核记录](../reviews/2026-10-19-load-measurement-review.md)。

计量回归覆盖计数抵消、窗口边界、重复观察、未完成 P99、调度等待、超时样本、终态失败分类和空分位数。真实 MySQL 的四张独立探针表验证：未提交不可见、提交后可见、旧凭证时间不影响结果、回滚不出现、不平凭证不算完成；测试结束删除这些私有探针表，不向业务账表写入探针资金。

各支付场景在本轮观察截止时，已返回 202 的支付全部过账，未完成 0、传输异常 0、容量未发 0、借贷差额 0、逐凭证不平 0。这不能把503计为成功；105 / 2517 / 2906 个失败 HTTP 在观察截止时未发现持久化订单，报告保留为未观察到，不能据此证明未来绝不提交。

第一轮 300 档超出第一组数据库采样结束时间，因此另做带诊断复测。诊断有启动耗时，实际首末采样时间见结构化结果；SQL 摘要增量是各诊断窗口内的聚合，**并非整个支付负载的逐笔耗时总计**。两次 300 档的差异也表明共享主机结果会波动，不选较高数字冒充容量。

## 已确认的主要限制

**入口配额更新热行。** 100/s 负载已出现 `api_rate_limits.PRIMARY` 上的 `X,REC_NOT_GAP` 等待；查询独立运行时同样出现，后台任务队列为 0。查询诊断窗内该 upsert 执行 2631 次，累计语句耗时 48.96s，锁耗时计数 39.99s；300 档支付诊断窗内 1421 次，分别 129.81s / 112.15s。等待图最多 66 条边，边数不是不同被阻塞连接数。签名过滤器对同一 key、同一秒更新同一条记录，竞争发生在业务处理之前。

**数据库连接被入口与后台共同占用。** 100 档采样活跃连接到 32、等待连接到 5；300 档到 32 / 14。纯查询只到 16 / 0，却已经有503，说明 API 在途上限也会限制入口。两类指标结合锁证据，支持先消除入口热行，而不是直接扩大池子。本轮连接获取超时计数未增长，不能沿用旧实验“池超时”当作本轮事实。

**本地数据库缓存与事务成本值得继续隔离。** 当前 InnoDB buffer pool 为 128MiB，表数据与索引估算合计约 1.22GiB。300 档诊断期间 buffer pool 物理读计数增加 38074，纯查询仅增加 30；支付诊断内 COMMIT 累计 7676 次 / 59.73s。当前 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`，未放宽持久性。没有磁盘延迟 / fsync 分解，不能把这些数字直接解释为磁盘已饱和，也不修改持久性换吞吐。

**后台积压与观察开销。** 300 档采样全局待处理任务指标最高 226，包含尚在运行的任务；该指标15秒刷新，不能当作瞬时精确值。支付完成 P99 已超过3秒。观察器 SQL 在对应诊断窗累计 59 次 / 3.61s、检查516594行；整个支付运行记录观察耗时5.53s、单次最多487ms、最宽提交区间698ms，后者包含轮询间隔。新观察器本身有成本，不能把它计作零开销或用成功 P99 上界越线直接证明每笔真实 commit 延迟越线；本次 P99 下界也已超过3秒。

当前空闲状态的领取 SQL 执行计划为索引范围、没有 filesort；观察器支付查询走业务号唯一索引范围，凭证和 Outbox 走唯一事件索引，分录走凭证索引。空闲执行计划不能替代满载时计划与等待采样，也不能宣称所有 SQL 已优化。

## 后续优化顺序

1. 先做配额热行的对照优化，保留每 key 每秒500次的既有契约、nonce防重放、全局背压和拒绝语义。候选方案需验证单机重启、多实例、额度边界与依赖失败；多 key 分流只能用于隔离诊断，不能代替单 key 热点修复。
2. 在固定 D0 资源上分别比较缓存预算、独立后台任务和事务往返成本；每次只改一个变量，继续核对唯一过账、退款上限和 Outbox，保留持久性要求。
3. 校准观察器开销与区间宽度，补多凭据、标准渠道成功 / 失败分布，再执行 R1 的预热、15分钟正式负载、D1 和长稳。当前单商户、当前日期工具不覆盖这些门槛。

本轮只运行计量工具回归、真实 MySQL 可见性测试、短时支付与查询负载和只读诊断。既有244项后端、前端及浏览器套件未整套重跑，也没有将历史结果改写成本轮验证。
