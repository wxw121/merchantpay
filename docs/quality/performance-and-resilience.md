# 性能、容量与韧性验收

日期：2026-10-17。关联：[需求说明书](../superpowers/specs/2026-10-17-merchant-payment-platform-design.md)、[三个版本](../roadmap/three-major-releases.md)、[技术基线](../architecture/technology-baseline.md)。

**本文件定义验收目标，不是达标报告。V1 已有可运行实现和 D0 实测，结果见 [V1 证据](../releases/v1.0.0.md)；300 完成 TPS、D1 全量和 R1 长稳仍未验收。**

## 1. 统一指标口径

| 指标 | 定义 |
| --- | --- |
| 支付完成 TPS | 每秒唯一支付单进入渠道成功已确认状态，且对应支付状态、有效账务和 Outbox 的本地事务已提交的数量 |
| 支付受理 QPS | 支付请求已校验并持久化受理的数量，包括最终失败的请求；不等同于支付完成 TPS |
| 回调确认延迟 | 从有效回调进入平台到持久化 Inbox 后返回确认的延迟；不是最终过账延迟 |
| 最终成功延迟 | 从平台接受支付到渠道成功确认及有效账务提交的端到端时间，含排队与异步处理 |
| 精确查询 QPS | 已存在支付号的单对象查询吞吐；不冒充报表、模糊查询或多表列表吞吐 |
| 系统错误率 | 约定正常负载下 5xx、非预期超时、丢失已受理请求的数量占有效请求比例 |
| 业务成功率 | 渠道成功支付数／有效支付受理数；另列确定失败、未知和未完成数量 |
| 数据新鲜度 | 业务事实提交到对应指标可查询的时间差，同时提供数据水位 |
| 账单处理时间 | 文件已完整进入对象存储后，到匹配、差错输出、合计与结果发布完成的时间 |
| 正确性失败 | 重复有效入账、借贷不平、超额退款、重复有效结算、未经审核调整、越权泄露之一 |

HTTP 200／202、压入队列、存入 Redis、消费 offset 增长和空接口响应都不能代替支付完成。若一个业务请求被重试十次，完成 TPS 中最多计一次。

受理吞吐、完成吞吐、队列长度和年龄同时报告。端到端延迟纳入未完成请求：报告未完成数量、等待时长与收敛结果，不能只统计最快完成的一部分样本。

开发负载器从计量 V2 起，使用独立 READ COMMITTED / autocommit 连接在一条 SQL 中读取成功状态、来源唯一凭证、至少两条且平衡的分录和对应 Outbox。以本机单调时钟记录“上次不可见查询开始—首次可见查询结束”的保守提交区间；数据库业务时间戳不用于 commit 计时。到达窗完成数与成功延迟分别报告上下界，另外报告从计划发送时刻开始的全体受理请求 P99 上界、未完成数量和最长等待年龄；不能约束的 P99 上界为 `null`。HTTP 超时保留为延迟样本，503 / 超时逐业务号查证，不能抵消另一笔 202 未完成。当前 250ms 轮询会引入连接、查询和缓存开销，必须同时披露观察耗时和区间宽度；本工具尚未完成 R1 测量开销校准。实现及 D0 证据见 [计量与瓶颈诊断](2026-10-19-d0-load-diagnosis.md)。

## 2. 环境等级

### 2.1 日常开发 D0

建议至少 8 核、16 GiB 内存和 100 GiB 可用 SSD；16 核、32 GiB 更适合并行运行前端、业务、数据库和观测组件。按 Compose profile 启动需要的组件，Flink／多副本 Kafka／完整数据库集群无需每天全开。

D0 验证功能、正确性和缩比流程。它不承担 V2／V3 的完整规模承诺。若实际设备更小，记录实际环境并相应缩减本地数据集，不降低最终参考环境门槛。

### 2.2 R1：V1 基础参考环境

| 组件 | 参考资源 |
| --- | --- |
| 业务与后台进程 | 合计 4 vCPU、8 GiB |
| MySQL | 8 vCPU、16 GiB、200 GiB NVMe |
| 独立模拟器 | 2 vCPU、4 GiB |
| 对象存储及基础观测 | 合计 2 vCPU、4 GiB |
| 独立压测机 | 4 vCPU、8 GiB，不与被测系统争抢资源 |

实例之间网络至少 1 Gbps，同地域，记录 RTT 和限速。以上资源可以来自独立容器或虚拟机，但要保证配额及负载隔离，不能把超卖核数当作独占资源。

### 2.3 R2：V2 可靠性参考环境

| 组件 | 参考资源 |
| --- | --- |
| 业务实例 | 3 × 4 vCPU、8 GiB |
| MySQL 单物理分片 | 三成员单主集群，每成员 8 vCPU、24 GiB、500 GiB NVMe |
| Kafka | 3 × 2 vCPU、8 GiB、500 GiB SSD |
| CDC／Connect | 合计 2 vCPU、4 GiB |
| ClickHouse | 4 vCPU、16 GiB、500 GiB NVMe |
| Redis | 2 vCPU、4 GiB |
| 模拟器 | 合计 2 vCPU、4 GiB |
| 观测、身份及对象存储 | 合计至少 4 vCPU、8 GiB，存储独立计量 |
| 独立压测机 | 2 × 4 vCPU、8 GiB |

数据库成员和 Kafka 副本分布在不同故障域。至少 1 Gbps 网络，报告网络瓶颈；不能在同一宿主机断一个容器后声称已验证机器故障。

### 2.4 R3：V3 完整规模参考环境

这是参考预算，是否能满足目标取决于实际 CPU、磁盘、网络和实现，必须测量。调整资源时保存前后配置及结果，不进行隐藏加机器。

| 组件 | 参考资源 |
| --- | --- |
| 业务／任务进程 | 4 × 4 vCPU、8 GiB，任务有独立配额 |
| MySQL | 4 个物理分片；每片三成员单主；每成员 4 vCPU、16 GiB、500 GiB NVMe |
| Kafka | 3 × 4 vCPU、8 GiB、1 TiB SSD，三副本 |
| CDC／Connect | 合计 4 vCPU、8 GiB |
| ClickHouse | 两个数据节点，每节点 8 vCPU、24 GiB、1 TiB NVMe；Keeper 三节点合计 3 vCPU、6 GiB |
| Flink | JobManager 1 vCPU、2 GiB；2 个 TaskManager，各 4 vCPU、12 GiB |
| Redis | 主／副本合计 4 vCPU、8 GiB；仲裁进程独立故障域 |
| 模拟器 | 2 × 2 vCPU、4 GiB，持久化存储与业务库分离 |
| 观测与身份 | 合计至少 4 vCPU、8 GiB |
| S3 兼容存储 | 三节点或同等持久化服务；自建时合计 6 vCPU、12 GiB、至少 3 TiB 原始空间，按冗余扣除可用空间 |
| 独立压测机 | 2 × 4 vCPU、8 GiB |

参考计算资源约 134 vCPU、388 GiB 内存，包含压测与辅助组件。物理部署必须额外预留宿主机和系统开销；该预算不是个人电脑配置要求，也不是已实测的最小成本方案。

核心数据节点内网建议 10 Gbps，记录磁盘 fsync、IOPS、吞吐、RTT、可用空间及 CPU 型号。至少预留 30% 磁盘空间；全规模数据与本轮新增负载都要纳入容量。

不能只在同一台个人电脑上启动这些逻辑节点就宣称获得这些资源和故障隔离。购买或租用资源另行由用户决定，需求文档阶段不执行付费资源操作。

## 3. 测试数据集与容量

### 3.1 数据规模

| 数据集 | 支付单 | 账务分录 | 业务事件明细 | 商户数 | 业务日期跨度 |
| --- | --- | --- | --- | --- | --- |
| D1，V1 | 100 万 | 500 万 | 1,000 万 | 1,000 | 30 天 |
| D2，V2 | 1,000 万 | 5,000 万 | 1 亿 | 10,000 | 180 天 |
| D3，V3 | 1 亿 | 5 亿 | 10 亿 | 100,000 | 365 天 |

以上分录及事件量可以超过下限；数据生成报告必须说明实际笔数、业务分布与记账模板。需要通过合法支付、退款、手续费和模拟渠道收款核销事件产生对应凭证，禁止填充不平衡分录凑数量。

D3 支付完整明细与分录按业务日期分为热 20%、温 50%、冷 30%。热为最近 30 天，温为第 31～180 天，冷为第 181～365 天；日期分布可以非均匀。热温权威数据保留 MySQL，冷明细经验证后归档至 S3，并保留在线支付控制记录、去重／路由索引和 ClickHouse 检索投影。在线控制记录包含原实付、累计退款、有效预占和费率快照，保证归档后的退款仍受原子额度约束。

实际装载证明必须列出各层真实行数、对象清单与摘要。1 亿支付单指全保留期内可查证的总规模，不等于全部事件永远放在一个在线 MySQL 表中。未决支付、退款及差错保持在线，不随年龄直接归档。

### 3.2 数据分布与异常注入

- 支付金额按长尾分布生成，含 1 分、最大金额边界及手续费舍入案例。
- 至少 10% 的成功支付发生退款；其中包含多次部分退款、并发退款、结果未知退款和已结算后的退款。
- 账单预置差异覆盖全部差错类型，每个种子保存独立预期答案；金额和笔数均有合计校验。
- 正常分布外另设热点场景：单商户承接 50% 支付；前 1% 商户承接 80% 支付；单支付 1,000 次／秒退款尝试。
- 历史数据包含已归档交易的重复业务请求、迟到通知、退款与查询。
- 数据生成种子、合法状态转换、凭证规则、事件 ID 和业务号的唯一性都需核对。

### 3.3 容量估算方法

初始估算采用：每支付单含索引约 1.5 KB，每分录含索引约 0.35 KB，每事件明细原始编码约 0.6 KB。D3 对应约 150 GB、175 GB 和 600 GB，合计约 925 GB，再加渠道证据、Outbox、退款、审批、归档清单、数据库日志和预留空间。

这些是规划假设，必须先装载至少 100 万支付的合法样本，测出实际行长、索引、压缩、冗余和日志成本，再修订完整容量。不能把压缩前后容量相混，也不能漏掉多副本、备份、归档和本轮压测新产生的数据。

## 4. 标准工作负载

### 4.1 模拟渠道条件

正常性能基线采用 98% 成功、2% 权威明确失败；渠道处理延迟 p50 50ms、p95 200ms、p99 400ms，并固定随机种子。回调额外排队延迟 p99 不超过 500ms。20% 成功通知重复一次；正常基线没有人为无限超时。

支付完成目标只计算成功且已过账的唯一支付，因此受理速率必须高于目标 TPS，并报告最终失败和在途量。模拟器保留独立的真实结果清单，核对平台是否遗漏或重复处理。

未知结果、长延迟、重复风暴、乱序和依赖不可用采用单独故障场景；不能混入基线后把这些样本从延迟统计中悄悄剔除。

### 4.2 C1：支付及退款写入链路

| 条件 | V1 | V2 | V3 |
| --- | --- | --- | --- |
| 支付完成 TPS | 300 | 2,000 | 5,000 |
| 同时退款完成量 | 支付完成量的 10% | 支付完成量的 10% | 支付完成量的 10% |
| 持续时长 | 15 分钟 | 30 分钟 | 60 分钟 |
| 预热 | 10 分钟 | 10 分钟 | 10 分钟 |
| 初始数据集 | D1 | D2 | D3 |

退款来自已成功支付的独立合法样本，不能向尚未完成支付的对象强行发起成功退款。退款重复率、失败率和延迟另行报告。一个写入峰值场景包含支付创建、渠道请求、回调持久化、状态转换、分录、Outbox 和退款处理，报告所有内部与外部请求量。

### 4.3 C2：独立精确查询

| 条件 | V1 | V2 | V3 |
| --- | --- | --- | --- |
| 查询 QPS | 2,000 | 8,000 | 20,000 |
| p99 | ≤ 200ms | ≤ 200ms | ≤ 200ms |
| 持续时长 | 15 分钟 | 30 分钟 | 30 分钟 |

此场景只查询在线已存在支付号，随机选择覆盖全部在线分片；80% 请求从完整在线数据范围随机选择，20% 为重复热点。报告缓存命中率，并另跑禁用业务缓存的对照组；对照组不强制相同峰值，但须披露结果及瓶颈。

创建后立即查询及支付状态判断走权威读或满足读己之写要求的路径，不把可能过期的副本／缓存状态当成成功或失败依据。

### 4.4 C3：混合业务与隔离

| 同时执行 | V1 | V2 | V3 |
| --- | --- | --- | --- |
| 支付完成 TPS | 150 | 1,000 | 2,500 |
| 退款完成 TPS | 15 | 100 | 250 |
| 精确查询 QPS | 500 | 2,000 | 5,000 |
| 列表查询 | 10 并发 | 20 并发 | 50 并发 |
| 对账任务 | 10 万行 | 100 万行 | 1,000 万行 |
| 异步导出任务 | 1 个 10 万行 | 2 个各 50 万行 | 4 个各 100 万行 |
| 分析查询 | 基础统计 5 并发 | 10 并发 | 20 并发 |

混合场景持续至少 30 分钟，V3 为 60 分钟。对比相同支付负载下关闭分析／对账／导出的基线，支付端到端 p99 增幅不得超过 20%，且系统错误率 ≤ 0.1%，核心不变量无违反。

列表默认单商户、最近 7 天、每页 50 条，p95 ≤ 500ms；不默认计算跨全库精确总页数。跨 365 天历史查证使用异步任务，单支付冷数据查证目标 60 秒内完成。

V3 常用分析模板为：最近 24 小时每分钟支付数／金额／成功率、单商户最近 30 天每日净收款、渠道最近 7 天错误与延迟分布、对账差异按日和类型汇总。20 并发下 p95 ≤ 3s，按已发布有效版本统计；任意临时 SQL 不在此响应承诺内。

### 4.5 C4：批处理与大数据

- 分别运行 10 万／100 万／1,000 万行渠道账单，目标 10／15／30 分钟；匹配本地支付与退款，输出差异明细及金额合计。
- V3 账单任务运行到 50% 时中断并恢复，最终结果与不中断运行按业务键和金额完全一致；重复运行不新增有效调整。
- D3 进行至少一次全部历史事件重放，记录总时长、资源、恢复位点与结果。全量重放目标 24 小时内完成，期间线上查询读已发布代，不暴露半成品统计。
- Flink 实时指标新鲜度 p95 ≤ 10s；迟到 30 天以上的数据进入重算通道，界面展示待修正范围，最终在相同封版水位核对一致。
- 100 万行导出在 10 分钟内生成，后台流式分页处理；客户端不持有全量结果，文件有摘要、生成水位、权限与失效期。

## 5. 通用延迟与稳定性门槛

| 指标 | 门槛 |
| --- | --- |
| 支付受理延迟 | p99 ≤ 300ms，不含尚未发生的渠道最终结果 |
| 回调持久化确认 | p99 ≤ 200ms |
| 支付最终成功延迟 | 正常渠道基线 p99 ≤ 3s，包含排队与过账 |
| 退款受理延迟 | p99 ≤ 300ms；最终完成单独计量 |
| 正常系统错误率 | ≤ 0.1%；业务明确失败另列，未知和未完成不得隐去 |
| 稳态核心 CPU | 平均 ≤ 70%，说明采样粒度及限制资源 |
| 运行空间 | 数据盘剩余 ≥ 30%；不得出现持续内存增长、OOM、连接泄漏或无界队列 |
| 事件积压 | 稳态不持续增长；正常 Outbox／CDC 事件到 Kafka p95 ≤ 5s |
| 长稳运行 | V1 4h、V2 12h、V3 24h；采用本版 C3 支付／退款／查询负载的 20%，每小时加入一次 5 分钟 C3 完整负载 |

长稳运行期间执行合法的重复通知、随机查询与退款，每小时校验增量账务，结束做整体核对。月度可用性设计 SLO 为 V2 99.9%、V3 99.95%；24 小时实验不能证明已经达成整月 SLO。

前端性能使用维护期 Chromium、1440×900 视口、4 vCPU／8 GiB 客户端、20 Mbps 下行与 40ms RTT；保留已认证会话但清空静态资源缓存，执行 30 次冷导航。商户工作台和交易列表的 LCP p75 ≤ 2.5s；关键操作在 200ms 内显示受理中、校验失败或等待反馈，后续业务完成按后端真实状态展示。1280px 桌面和 375px 收银页另跑端到端交互与布局测试。

## 6. 正确性与故障场景

| 用例 | 注入条件 | 必须观察到的结果 | 最迟版本 |
| --- | --- | --- | --- |
| FT-01 | 同一商户业务号 100 并发请求，含参数冲突 | 一个支付对象；冲突请求拒绝；无重复有效记账 | V1 |
| FT-02 | 同一成功事实 100 次通知，事件 ID 可不同 | 按业务事实去重，最多一次有效记账 | V1 |
| FT-03 | 查单与回调并发，旧失败通知晚到 | 正常状态不回退；矛盾权威证据进入差错流程 | V1 |
| FT-04 | 渠道已成功但响应与通知丢失 | 保留未知，使用原请求身份查证并最终正确过账 | V1 |
| FT-05 | 实付 100 元，同时申请退 80 元和 30 元 | 不超额；最多接受可覆盖的申请，拒绝其余；不自动改退款金额 | V1 |
| FT-06 | 退款请求超时或进程中断 | 预占保留；查证后正确结转或明确失败释放 | V1 |
| FT-07 | 微小金额多次部分退款、完成顺序打乱 | 最终累计手续费等于规则值且不超原手续费 | V1 |
| FT-08 | 状态与分录提交后、事件发出前终止进程 | 重启后事件继续送达，原分录不重复 | V1 |
| FT-09 | 消费事务已提交，提交 offset 前崩溃 | 重读后目标业务不重复执行 | V2 |
| FT-10 | CDC 暂停 30 分钟后恢复 | 事务和事件不丢失，积压在恢复后 30 分钟内回补 | V2 |
| FT-11 | Kafka 单节点故障、失去最小同步副本 | 前者继续或短暂恢复；后者可控积压／拒绝新受理，已受理不丢 | V2 |
| FT-12 | Redis 故障或缓存集中失效 | 正确性不变；保守限流与受控回源，不冲垮 MySQL | V2 |
| FT-13 | MySQL 主成员在写入中被终止 | 按承诺恢复；已确认写不丢，未确认请求可安全重试查证 | V2 |
| FT-14 | MySQL 分片失去多数派或旧主隔离 | 该分片停止受理写入，旧拥有者不能继续写 | V2 |
| FT-15 | 单商户 50%／前 1% 商户 80% 流量 | 正确性不变；V3 混合吞吐至少均匀分布目标的 80%，p99 不超过其 2 倍 | V3 |
| FT-16 | 单支付每秒 1,000 个退款尝试 | 限流或串行化受控；零超额；其他支付吞吐下降 ≤ 20% | V2 |
| FT-17 | 部分账单、重复账单、新账单版本、金额冲突 | 结果版本明确；不可半份封版；不自动据冲突文件改账 | V2 |
| FT-18 | 本人审核、审批后金额变化、执行中断 | 绕过被拒；审批失效；恢复不重复调整 | V2 |
| FT-19 | 同一数据代事件重放 3 次，ClickHouse 暂停合并 | 查询与最终指标不增重，不能依赖等待合并“自然正确” | V3 |
| FT-20 | 31～365 天历史事件及已归档支付退款 | 去重和路由有效，旧事件走修正通道，不当作新收入 | V3 |
| FT-21 | 迁移逻辑桶时并发支付、退款、回调 | fencing 有效；核对一致；不重复收费、记账或结算 | V3 |
| FT-22 | 仅用备份与远端日志重建环境 | 恢复到声明水位，核对恢复点后未决业务，满足 RPO／RTO | V3 |
| FT-23 | 越权查询、游标篡改、导出链接转交 | 未授权用户无法读取数据，记录拒绝与审计证据 | V1；V3 规模回归 |
| FT-24 | 跨分片结算部分预占后崩溃 | 可恢复／释放；同一来源没有重复有效核销 | V3 |
| FT-25 | 已模拟结算后退款，商户净额变负 | 产生负向结转，原结算单不变，不生成负数出款单 | V2；V3 跨片 |
| FT-26 | 密钥轮换、伪造／过期签名及通知重放 | 轮换期按策略验证，伪造拒绝，合法重试不重复执行 | V2 |
| FT-27 | 以本版 C3 两倍负载持续 5 分钟 | 明确限流与背压，无 OOM 或无界队列；恢复后 10 分钟内回稳 | V2 |
| FT-28 | Flink checkpoint 中断、作业重启、全量重建新代 | 水位可追踪；未校验新代不发布；最终统计与权威事实一致 | V3 |

FT-10 的回补期间暂停非必需导出并记录资源；入站负载固定为本版 C3 的 20%，不能一边使用更低负载一边声称达标。积压回补速率至少超过正常流入量，且保护支付处理。

## 7. RTO、RPO 与可用性边界

| 故障范围 | V1 | V2 | V3 |
| --- | --- | --- | --- |
| 应用进程中断 | 5 分钟内恢复，已持久化确认数据 RPO 0 | 60 秒内恢复，已持久化确认数据 RPO 0 | 30 秒内恢复，已持久化确认数据 RPO 0 |
| 单个 MySQL 成员故障，多数派健在 | 备份恢复演练，不承诺自动切换 | RTO ≤ 120s；已确认写 RPO 0，按确认策略实测 | RTO ≤ 60s；已确认写 RPO 0，按确认策略实测 |
| 分片失去多数派 | 停写，人工恢复 | 停写，人工恢复 | 停写，保护正确性，不计为零中断 |
| 单个 Kafka 节点故障 | 无 Kafka | RTO ≤ 120s，已确认事件不丢 | RTO ≤ 60s，已确认事件不丢 |
| 完整集群损毁，依赖远端备份 | 记录实际恢复点和时长 | 验证恢复步骤 | RPO ≤ 5min、RTO ≤ 4h |
| 桶迁移切换 | 未启用物理迁移 | 验证路由语义 | 预先同步后冻结阶段目标 ≤ 60s，按实际桶规模记录 |

RPO 0 仅针对表中明确的单进程／单成员故障范围，前提是耐久与复制确认策略生效并有核对证据；不延伸为机房、所有副本和备份同时丢失也零损失。

完整集群恢复采用日全量备份和持续远端日志归档，归档间隔不超过 1 分钟，并实测端到端恢复点。恢复点之后的渠道事实进入查单／对账处理，不伪造已经恢复的账务记录。业务侧按无法确认的范围冻结结算并显示查证状态。

备份清单记录每个物理分片的 GTID／提交水位、控制配置版本、结算任务状态及归档清单摘要。跨分片不假设天然存在同一时刻快照；恢复后先冻结结算与调整写入，校验来源分配和在途任务，再按各分片水位恢复处理。

## 8. 观测与告警

必须有请求速率、成功／失败／未知比例、支付最终延迟、连接等待、锁等待、死锁、CPU、GC、内存、磁盘、MySQL 复制状态、Outbox 最老事件年龄、CDC 位点、Kafka lag、Flink checkpoint、ClickHouse 合并／写入及数据水位。

业务告警至少覆盖：疑似重复入账、借贷不平、退款额度异常、未知订单超时、账单未到／合计不符、差错未处理、结算来源重复、预占长时间未释放、导出越权及审批绕过。任一资金不变量违反即阻断发布，并可冻结对应商户结算流程。

指标标签不得使用无限增长的订单号、用户号或 trace ID；这些标识通过日志与追踪关联。金融明细和请求体默认脱敏，不在观测平台复制密钥。

## 9. 压测方法与报告证据

1. 数据生成器先准备对应规模，执行约束和合计核验；记录清单、种子、截止水位和实际占用。
2. 固定环境、镜像、数据库结构、耐久参数、线程／连接配额、索引和渠道延迟；独立确认压测机不是瓶颈。
3. 使用 k6 开放到达模型运行 C1／C2／C3，报告目标与实际请求率、丢弃迭代、错误、在途及队列；避免系统变慢时客户端自动降速而掩盖排队。
4. 正式性能场景至少独立运行 3 次，全部达到吞吐及正确性门槛，逐次报告 p50／p95／p99 和资源；不能只挑最好一次。
5. 独立故障场景执行指定注入，测量实际 RTO／RPO、已受理请求恢复和账务核对。业务拒绝、系统错误及未知分别统计。
6. 每次测试结束从模拟渠道权威结果、支付单、退款、凭证／分录、Outbox／消费记录和报表按业务键核对；全量不变量校验与增量事务核对并行使用。
7. 报告前端交互与后端结果的端到端验证；对错误、无权限、结果未知和重算状态进行截图或录屏取证。
8. 提交原始数据、报告、执行命令、环境清单、镜像摘要和缺陷清单；不能只交一张 QPS 截图。

开放与闭合负载模型的差异参考 [Grafana k6 官方说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。本项目所有具体阈值属于需求目标，官方资料不提供项目达标保证。

## 10. 每版签署条件

版本报告逐项列明 FR、NFR、CH 与 FT 的覆盖关系及结果。V1／V2 可使用对应规模；V3 必须使用 D3 与 R3 或资源和故障隔离不低于其标准的明确环境。

功能通过但没有执行全规模验证时，写明“规模验收未完成”；外部沙箱未联调时写明“外部接入未验证”。任何核心不变量失败、高危权限漏洞或没有来源证据的账务调整，都不能被吞吐达标抵消。
