# V1 支付路径与任务隔离优化

测量日期：2026-10-22；复核及本地部署：2026-10-23。延续前一轮 HTTP 池/后台并发优化；Kafka 仍属于 V2。本轮不发布。

**结论：支付单项对照有收益，整体性能目标仍失败。** 保留路径/队列/配额/锁改造，连接池隔离保持默认关闭。最终混合负载为 52.12 支付 TPS、16.95 退款 TPS，目标查询负载为 752.53 成功 QPS；错误、未发送及尾延迟均不满足要求。

## 已验证的支付优化

同一资源配置下，支付 100 次/秒的 A/B/A 对照得到成功完成吞吐 **83.17 → 94.18 → 79.28 TPS**。候选高于两组原版约 13%～19%，503 从 630/890 次降为 176 次，但仍未满足 300 支付 TPS、同时 30 退款 TPS 的要求。

| 60 秒支付窗口 | 成功完成 TPS | 系统错误 | HTTP P99 | 成功完成 P99 |
| --- | ---: | ---: | ---: | ---: |
| A1：上一轮保留版本 | 83.1667 | 630 | 1898.581 ms | 4422.436 ms |
| B：本轮组合优化 | 94.1833 | 176 | 1598.341 ms | 3574.775 ms |
| A2：恢复上一轮版本 | 79.2833 | 890 | 1626.808 ms | 4703.177 ms |

每组先预热 60 秒，再测量 60 秒。应用 2 CPU/1 GiB，MySQL 2 CPU/2 GiB、缓存 1 GiB、双 1；数据库连接总数 32，入口在途 128，后台 FAST 总并发 96。数据库及模拟器未重启、金融历史未清除。数据来源为 `.work/acceptance/commit-aba-pay-20261022T105349/summary.json`。共享主机 D0 的短窗口对照不构成 R1 资格认证。

完成 TPS 按独立连接在到达窗口内观察到成功业务、平衡凭证和 Outbox 已提交的唯一业务数计算。HTTP 202、窗口结束后才完成的交易和重试均不能增加该数。上表 HTTP P99 包含错误响应；成功响应的独立 P99 从逐请求样本另外重算，不将两种口径混为一谈。

## 代码变化及边界

1. 新建支付直接使用唯一约束插入，再在冲突时读取旧业务号并验证参数。正常新建少两次支付表 SELECT；禁用商户的已有支付重试仍能幂等返回。返回时间与数据库统一到微秒。
2. 首次新建且首次领取的渠道任务，在 PREPARED 持久化后直接提交。已准备、结果未知、重领及关闭任务继续先查询。正常支付少一次渠道查询及对应原始回执更新；回执仍先于资金结果事务独立落库。
3. FAST、INBOX、NOTIFY 三类任务分别领取，性能配置为 64/16/16，BULK 另有 2 个名额。堵塞的商户通知不能用尽回调处理与渠道提交的名额。总并发不增加，小预算 1/2 仍有全局限制和轮转公平性。
4. 已存在且能容纳整批的配额窗口采用一次条件 UPDATE，避免后续 SELECT；新窗口和跨越固定秒 500 次边界继续精确分配。原来的 10 ms 聚合不算新增优化。nonce 仍逐请求先持久化。
5. 支付终态在同一资金事务内，先写凭证及事件，再释放准入桶。共享桶不再覆盖前面的记账 SQL；支付根行锁、原子提交及未知结果占用容量均保留。

未修改签名协议、每 key 每秒 500 次配额、幂等摘要、资金隔离、租约 fencing、双 1 和既有金融历史。

## 未采纳的单项实验

只启用新建支付 SQL 与首次渠道提交改造时，对照为 76.52 → 73.87 → 66.20 TPS，不能证明稳定收益。因此不把这两项单独宣称为吞吐提升；最终以整组隔离/配额/锁改造后的对照为依据。原始失败和错误样本保留在 `.work/acceptance/commit-aba-pay-20261022T102053/`。

## 数据库连接隔离候选

在相同总计 32 个连接内，用 Java 25 ScopedValue 区分 API 与后台执行角色。API 12 个、后台 20 个；回调、领取、异步任务、心跳、清理及定时指标明确进入后台角色。事务连接绑定仍使用同一个主 DataSource，事务中切换角色不会换连接。

该候选默认关闭。后台至少保留 3 个连接，避免两个 BULK 流读取占满连接后检查点无法提交。真实连接池测试覆盖 API 池耗尽时回调/领取/确认/指标继续运行，以及事务内角色切换的一致回滚。

相同组合优化代码的连接池对照如下，每组预热 60 秒、测量 30 秒。运行时 Hikari 指标核验隔离组恰为 12+20，未增加连接。

| 连接池 A/B/A | 完成 TPS | 503 | HTTP P99 | 成功完成 P99 |
| --- | ---: | ---: | ---: | ---: |
| A1：共享 32 | 95.0333 | 25 | 1283.349 ms | 2710.199 ms |
| B：API 12/后台 20 | 91.5333 | 92 | 1942.092 ms | 2651.369 ms |
| A2：共享 32 | 91.8000 | 148 | 1628.849 ms | 4418.644 ms |

隔离组没有证明吞吐收益，HTTP P99 弱于两组共享池对照；最终默认配置继续共享 32 个连接。保留已测试的显式隔离开关用于验证后台进展，**不宣称它提升并发，也不默认启用**。启用需要 `DATABASE_ISOLATION_ENABLED=true`，API 预算为 `DATABASE_API_CONNECTIONS`（默认 12），后台等于总池预算减 API；非法预算启动失败。原始记录：`.work/acceptance/commit-aba-pay-20261022T112946/`。

## 升级与回滚

V13 将未完成的回调及通知任务迁入 INBOX/NOTIFY 队列，保留任务 ID、重试数和租约。升级前必须停止负载并排空，停止所有旧 API 写入实例和 worker，再升级启动；新旧生产者不支持混合滚动。回滚也先排空并停止全部新实例，不能让旧 worker 遗漏新分类任务。已完成历史不需要改写。

## 验证与剩余门槛

全量 `fmt:format test fmt:check` 完成，平台 338 项、模拟器 6 项，共 **344 项通过，0 失败/错误/跳过**，含真实 MySQL 与本机 S3 HTTP。日志：`.work/flow-optimization-20261022/final-database-backend.log`。新增测试先证实原实现的 SQL 次数、通知挤占、配额读取、准入锁与小预算公平性问题，再验证修复。

最终混合压测的一次预检发现 32 个凭据商户仅有 1596 笔可退款成功支付，少于 1920 笔需求，因此负载未启动。该失败记录保留；随后通过真实签名支付 API 补充订单后再测，不直接插入成功状态或删除历史。查询覆盖这 32 家商户全部在线支付，包括初始 1024 笔与本轮新增订单；逐份原始报告记录 `queryPoolPayments`，不称为完整 D1。

## 最终目标复测

使用最终镜像、共享 32 连接、相同应用/数据库资源，32 个真实商户凭据，标准渠道与真实 HTTP 通知。每个到达窗口 60 秒，金融交易均观察到终态且资金/渠道事实及通知最终收敛。成功 TPS 仅统计窗口内已提交的成功平账业务。

| 负载 | 实际成功吞吐 | 系统错误 / 未发送 | 成功 HTTP P99 | 判定 |
| --- | --- | --- | --- | --- |
| 支付 310/s + 退款 32/s | 52.1167 支付 TPS / 16.9500 退款 TPS | 支付 15144 / 0；退款 757 / 0 | 支付 3718.655 ms；退款 3494.682 ms | 300/30 TPS 与延迟失败 |
| 查询 800/s | 717.6333 QPS | 2539 / 2379 | 3416.435 ms | 本档也未通过 |
| 查询 2050/s | 752.5333 QPS | 29479 / 47094 | 4572.031 ms | 2000 QPS 与延迟失败 |

混合支付成功完成 P99 为 8964.326 ms，退款为 9035.920 ms，均超过 3 秒；成功受理 P99 超过 300 ms，查询超过 200 ms。目标查询的系统错误包括 29078 次入口在途拒绝和 401 次传输失败，另有 47094 个计划请求未发送；不能把少发的请求从负载分母排除。800/s 查询也包含 161 次传输失败。没有 429，不是每 key 500/s 配额导致这些失败。

混合支付的 503 分为入口在途 7046 次、支付积压容量 8098 次；退款 757 次均为入口在途拒绝。它们说明拥塞最终在哪里被拒绝，不能仅据此证明首要根因或推断服务器已经到极限。当前证据不支持“整体吞吐已达标”或“查询性能提高”的结论。

补充订单的 30/s、30 秒窗口达到 29.1333 成功支付 TPS、0 系统错误，但成功受理 P99 623.001 ms；这只是已测档位，也没有通过完整延迟要求，不能作为最大容量。各场景不能拼成同时支持的三项容量。
