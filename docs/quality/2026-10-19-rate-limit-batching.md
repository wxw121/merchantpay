# V1 配额热行优化与对照验证

日期：2026-10-19。承接[计量与瓶颈诊断](2026-10-19-d0-load-diagnosis.md)。用户已授权实现限流热行优化及对照压测；不改变每 key 固定秒500次、持久化nonce、防重放、租户和业务幂等契约。

## 设计与边界

现有签名过滤器每次请求分别提交nonce、更新同一配额行、读取累计值。多请求争抢一条配额行已在实际锁等待中确认。此轮仅优化配额更新，不同时调整数据库缓存、池32、API在途16、FAST/BULK后台容量或持久性配置。

采用 `ApiRateLimiter` 对同一 key / 服务端秒的并发检查设置10ms聚合等待目标（线程调度可能增加实际等待）：

1. 请求仍先验证签名并持久化nonce；失败或重放不进入配额批次。固定窗口沿用过滤器收到请求时捕获的服务端秒，不用客户端签名时间划窗。
2. `ConcurrentHashMap.compute` 串行化同一窗口入队。虚拟线程领取并移除整个批次后独占其列表；后续请求建立新批次，互不修改已领取列表。
3. 同一数据库事务增加批量计数、读取累计值，提交后才分发结果。批次跨过500时，只允许剩余额度对应的请求；被429拒绝的有效请求仍计入窗口，与原契约一致。
4. 多实例仍竞争数据库中的唯一窗口行，既不分别初始化500额度，也不缓存一批尚未使用的额度。进程重启后读取已持久化窗口；关闭、事务/提交异常或无法确认结果时返回可重试503，不放行。
5. 配额事务超时3秒、调用等待最多5秒。调用中断或超时不会回退可能已提交的计数，避免不确定情况下重复发放额度；这类请求可能消耗配额而未进入业务，应按原业务号、新nonce退避重试。
6. 未结束的JDBC / COMMIT使用独立工作许可，容量与 `API_MAX_INFLIGHT` 相同；调用超时不释放该许可。无法启动新工作时直接503。关闭等待最多5秒，再请求中断；不能保证驱动中断能撤销已经发出的COMMIT，因此关闭后不再向业务发放额度，未知计数保持保守。

代价是低负载请求增加一次目标10ms的聚合等待，以及一笔显式短事务；高并发是否受益由对照测量判断。API在途限制继续约束等待请求量。批次大小取决于真实并发，稀疏请求可能仍是单笔，不承诺固定倍数收益。

选择该方案是为了在V1既有MySQL和JDK能力内降低写频率。仅加进程内限流不能保留多实例和重启语义；提前租用整块额度可能浪费剩余额度；Redis配额属于后续版本，新增依赖及其故障恢复语义不在这次单变量优化中。数据库中的窗口行仍存在，不能宣称彻底消除所有竞争。

没有新增表或迁移，已有 `api_rate_limits`、清理周期和500上限继续使用；签名API的429与503响应语义保持原样。

这轮已验证限流行写入频率和锁等待明显下降：支付采样中的等待边峰值45、查询66，批处理版两档均未采到等待边。SQL累计锁耗时仍非0，不能将“采样未捕获等待边”解释为完全没有竞争。累计语句秒数会叠加并发工作，不等于墙钟时间。

**吞吐改善伴随过载排队延迟退化。** 入口受理约215/s，窗口完成仅132–141/s，尚未达到稳定收支平衡；停止发送后才排空。后台待处理/运行指标峰值从494增至1664，该指标15秒刷新，不能当作逐时刻精确队列。P99下界也已超过6秒，不能归咎于采样误差后忽略。

本轮没有同时调整后台并发、数据库池、缓存预算或持久性来掩盖这个结果。接下来的优先项是**异步积压背压与后台处理能力**：约束已受理未完成工作量，再分别测任务事务成本、连接分配和缓存/读盘。当前buffer pool仍为128MiB；支付诊断物理读计数旧版增加43634、批处理版113653，接受更多业务后I/O工作也增加，尚无磁盘延迟分解，不能直接断言磁盘饱和。

观察器同样有开销：本轮最大观察区间旧版1.166s、批处理版1.474s，已在TPS/P99区间中保守体现。短时窗口包括启动/JIT、共享主机、缓存与库规模变化，未做正式10分钟预热；结果不构成容量提升倍数保证。300完成TPS、2000查询QPS、D1和R1长稳仍未验收，两个300请求/s负载仍因503而失败。当前版本继续为 `1.0.0-SNAPSHOT`。
